# Nextcloud × WeKnora 企业文件与知识平台开发计划

创建日期：2026-09-22；更新日期：2026-09-23。版本：0.3。状态：产品需求与开发计划草案，可拆分任务执行，尚未实施。

版本 0.3：补充 Nextcloud 端触发判定及发布操作（第 7.8–7.12 节），明确自动目录发布与人工确认发布的边界、不同文件替代关系和验收条件。新增内容为待开发需求。

版本 0.2：补充文档版本发布、失效与资源回收 PRD（第 7.1–7.7 节），明确产品行为、默认参数、持久化回收模型及验收要求。这些为拟开发能力，不表示当前 WeKnora 已支持。

目标：增加独立 Nextcloud 部署项目与原生集成应用，让员工统一管理文件，将授权目录自动发布到 WeKnora，并逐步在 Nextcloud 中提供个人身份下的 AI 问答。

本文按尚未正式部署设计。工作区存在本地开发与 AD 接入记录，不视为正式部署或生产验收结果。不在本计划阶段更改现有服务、企业 AD 或部署环境。

## 1. 基线与决策

已检查 WeKnora-ldap-ad 的 datasource/connector.go、types/datasource.go、application/service/datasource_service.go 的文件存在性、router/routes_knowledge.go、LDAP_AD.md 及本地接入说明。现有基础包括 AD 身份和组授权、知识库权限、受限 API Key、外部数据源全量/增量/流式接口、异步解析与索引。尚未发现 Nextcloud/WebDAV 连接器。

推荐决策：

1. Nextcloud 维护文件原件、目录、版本和共享；WeKnora 维护可重建的知识副本、解析结果与索引。
2. 开发 Nextcloud 原生应用 integration_weknora，不修改 Nextcloud 核心源码；PHP 后端及 TypeScript/Vue 前端，具体依赖跟随选定 Nextcloud 版本兼容矩阵。
3. WeKnora 添加 nextcloud 数据源连接器，复用现有同步调度和入库队列。首版不新增独立同步微服务。
4. 插件记录变更，通知 WeKnora 拉取；定期完整清单核对补偿漏报。数据库事件表提供持久化可靠性，通知仅是唤醒信号。
5. 首版为受控部门知识发布：一个权限范围一致的目录绑定一个专用知识库。个人文件、任意共享及复杂 ACL 是后续独立版本。
6. 用户问答使用个人身份；同步机器凭证不能替代用户授权。
7. 初期一个知识库只绑定一个发布目录，禁止重叠绑定，降低删除、权限和内容来源混淆风险。

| 版本 | 包含 | 交付边界 |
| --- | --- | --- |

```text
ai-server/

  nextcloud-weknora/            # 独立发布的 Nextcloud 应用
    appinfo/                   # info.xml、路由与依赖声明
    lib/AppInfo/               # 注册服务和事件监听
    lib/Controller/            # 配置、绑定、清单、读取、授权接口
    lib/Service/               # 发布策略、事件记录、签名、状态服务
    lib/BackgroundJob/         # 投递、核对与清理
    lib/Db/                    # 表映射和查询
    lib/Migration/             # Nextcloud 应用数据库迁移
    src/                       # 管理页面、文件侧栏与状态展示
    tests/                     # 单元、集成及前端测试
  WeKnora-ldap-ad/              # Go 连接器、权限与同步扩展
```

Nextcloud 使用独立数据库和 Redis 服务；WeKnora 延续原有数据库、Redis、解析服务与向量存储。开发时统一 Compose 编排，生产按容量拆分。两边文件卷独立，不直接读取另一系统数据库或存储目录。

部署产物锁定镜像版本及摘要，不使用 latest。P0 选择当时受支持且与 LDAP、团队文件夹应用共同兼容的 Nextcloud 版本，记录 PHP、数据库、Node 构建版本及插件依赖锁文件。本文引用 stable 文档用于接口研究，不据此直接锁定生产版本。

## 4. 用户流程与界面

管理员流程：安装插件 → 配对连接 → 测试连通性与权限 → 选择发布目录 → 映射 AD 组和专用知识库 → 预览文件数量、大小、格式及权限例外 → 启用 → 首次同步 → 查看进度和失败原因。

员工流程：在部门目录上传/编辑 → 文件侧栏显示待同步/解析中/可问答/失败/不支持 → 点击“在知识库中提问” → 以个人账号访问 WeKnora → 从引用返回 Nextcloud 原文。

页面至少包含：系统连接设置、目录绑定列表及编辑、同步任务与失败列表、文件侧栏状态、重试/暂停/解除绑定操作。只有目录发布管理员能绑定；普通员工只能查看自己有权访问文件的状态。错误不泄露其他目录名称或机器密钥。

暂停自动同步与停止发布分开：前者允许已发布内容在授权仍有效时继续检索，后者立即阻止检索并启动清理。解除绑定默认先停止发布，不删除 Nextcloud 原件；界面明确知识副本清理结果。

## 5. 数据模型

以下为建议逻辑模型，P0 与现有表比对后确定迁移，避免重复建设。

| 所属 | 模型 | 主要字段与约束 |
| --- | --- | --- |
| 插件 | connection | instance_uuid、服务地址、协议版本、key_id、加密密钥、状态 |
| 插件 | binding | binding_id、root_file_id、tenant_id、kb_id、AD 组映射、policy_revision、状态 |
| 插件 | outbox | event_id、binding_id、file_id、事件类型、顺序号、时间、投递次数、下次重试时间 |
| 插件 | policy_state | 绑定的授权版本、检查时间、例外情况、是否可发布 |
| WeKnora | 现有 data_sources | 新增 nextcloud 类型，复用加密配置、游标、同步记录 |
| WeKnora | source_mapping | source_id、instance_uuid、file_id、knowledge_id、etag、indexed_revision、状态 |
| WeKnora | inbox/checkpoint | connection_id + event_id 唯一、已持久化游标、任务租约 |
| WeKnora | publication_state | binding_id、policy_revision、禁用状态、同步状态、错误类别 |

来源身份使用 instance_uuid + file_id，映射唯一键包含 data_source_id；路径可变，不作身份。Nextcloud 备份恢复后保持实例身份；克隆成新实例时重新生成实例身份并配对。

文件内容状态与权限状态分别记录。ETag 是变化令牌，不假设是内容哈希；必要时另算哈希去重。快照需要 generation、完整标记及分页游标；不以扫描开始时间伪装成一致性快照。

## 6. 接口契约

以下路径是拟新增接口，不是当前已存在的功能。P0 输出 OpenAPI 和双方契约测试。

| 方向 | 拟议接口 | 语义 |
| --- | --- | --- |
| WeKnora → 插件 | GET /apps/integration_weknora/api/v1/capabilities | 协议、格式、功能与实例身份协商 |
| WeKnora → 插件 | GET .../bindings/{id}/manifest | 分页清单，文件 ID、ETag、大小、类型、来源链接、generation |
| WeKnora → 插件 | GET .../bindings/{id}/changes?cursor=... | 持久化变更与删除墓碑；游标过期返回明确重扫标志 |
| WeKnora → 插件 | GET .../bindings/{id}/files/{fileId}/content | 流式内容；校验目录归属与当前版本，支持条件读取 |
| WeKnora → 插件 | POST .../bindings/{id}/authorize | 按服务端验证的用户身份，返回当前发布范围的 allow/deny 与权限版本 |
| 插件 → WeKnora | POST /api/v1/integrations/nextcloud/events | 批量变更提示，持久化 inbox 后返回 202 |
| 插件 → WeKnora | GET /api/v1/integrations/nextcloud/bindings/{id}/status | 配对范围内的同步和解析状态 |

绑定配置通过插件后端与 WeKnora 管理能力协调，采用 pending → active 两阶段，失败可重试和补偿；前端提交的 tenant_id/kb_id 必须由后端验证，不能直接信任。

服务间使用 TLS 和可轮换的连接级凭证。通知采用签名请求：key_id、时间戳、nonce、规范化方法/路径/查询及正文哈希参与 HMAC；校验时间窗、防重放、固定目的地址和绑定范围。内容下载端点只接受已配对目录内文件，不接受调用方任意 URL。配置地址与重定向需防 SSRF；企业内网地址按管理员批准的端点范围允许。

密钥仅在服务端保存，日志脱敏，支持短期双密钥轮换。管理浏览器请求使用 Nextcloud 会话及 CSRF 防护；机器接口单独认证。429/5xx 可重试，401/403 停止并告警，404/不可见不能直接推断为文件永久删除。

## 7. 同步算法与一致性

1. 初次同步生成清单，分页拉取支持的文件，经过原有格式/大小/解析配置校验入库。分页检查点只在结果持久化成功后推进。
2. 文件变更监听只记录事件，不执行网络下载或 AI 解析。后台合并短时间连续保存，通知 WeKnora；插件事件持久化不假定与 Nextcloud 文件写入共用事务，因此必须有定期核对补偿。
3. WeKnora 使用每绑定/文件互斥或租约处理，重新读取当前状态，避免乱序事件回滚内容。下载前后验证版本，发生变化丢弃旧结果并重试。
4. 任务使用来源身份及目标版本幂等键；记录下载、入库、解析完成分别的状态，不把 HTTP 上传成功当作可检索。
5. 新版本解析成功后切换可见版本；当前流水线若不支持原子切换，需实现可见性屏障，失败时不能混合展示新旧片段。旧版本是否保留可检索由产品策略决定，首版显示过期且默认不继续提供旧答案。
6. 改名仅更新元数据；移入目录触发入库，移出立即禁止检索。跨目录移动按源撤回、目标重新授权发布处理，不沿用旧权限。
7. 确认删除先设置不可检索状态，再清理知识记录、向量、图片、摘要及 Wiki 引用。墓碑保留到消费者确认且超过恢复窗口，防止旧任务复活内容。
8. 全量核对仅在完整遍历成功且扫描期间变化已协调后执行差异删除。部分失败、断网和权限拒绝不进行批量物理删除；权限不明时先关闭相关访问。
9. 游标丢失/过期进入受控全量核对，不能清空历史后盲目重建。重试指数退避加抖动，耗尽后进入失败列表，管理员可重放。

建议起始参数：内容合并窗口 10 秒、增量兜底 5 分钟、全量核对每日一次，均可配置并通过试点调整。后台 worker 的实际执行频率必须支撑目标，不能将默认 cron 周期误称为秒级实时。

### 7.1 版本回收的产品目标与当前缺口

目标：员工不会得到未标明的过期答案；更新失败不会提前销毁可恢复数据；历史索引不无限膨胀；撤权不依赖物理删除完成；每一次回收均可追踪、重试及核对。

2026-09-23 代码核对：datasource_service.go 当前同来源更新采用先 DeleteKnowledge，再尝试 HardDeleteKnowledge，随后重新创建；部分查询/删除失败仅记日志后继续。knowledge_delete.go 会清理索引、分块、图谱、Wiki 关联、知识记录和文件，但物理文件等清理失败存在尽力而为路径。因此现有逻辑不能作为可靠版本发布/回收的完成实现。

推荐采用分层保留：Nextcloud 负责文件历史，WeKnora 只保留当前可问答版本、短期恢复副本及必要元数据。默认不为每个历史版本长期保存向量索引。保留期是允许回收的条件，不是删除一定完成的承诺。

### 7.2 发布方式与员工体验

V1 默认采用“严格最新”模式：发现源文件变化后，旧版本停止参与新问答；新版本验证成功后才重新开放。界面显示“更新中”或“更新失败，暂不可问答”，保留失败原因及重试入口。保留旧副本不自动授予旧内容访问权。

另提供“审核发布”模式作为 V1.1 可选能力：员工编辑草稿目录，授权发布者将确认版本发布到专用目录，WeKnora 只跟踪发布目录。已发布内容持续有效，直到发布者提交下一版本。发布必须固定具体文件版本/内容摘要并记录操作者，不能把编辑中的最新文件误认为已审批版本。V1 不引入复杂审批工作流。

不提供自动静默回退到旧答案。恢复历史内容应优先在 Nextcloud 恢复后重新发布，生成新的发布代次；管理员可在当前权限允许且留有审计记录的条件下使用恢复副本重新构建，不能把旧代次直接改回当前代次。

文件侧栏分别展示：源文件更新时间、当前发布版本、知识就绪时间、更新失败原因。历史回答引用绑定原回答使用的版本；旧版本已回收时标明“该回答引用历史版本”，打开当前文件必须明确提示版本差异，不能把新原文冒充旧证据。历史回答不自动重写，撤权仍按第 8 节限制重新展示。

### 7.3 版本与可见性状态

文档拥有稳定来源身份，发布代次单调递增。内容版本由来源变化令牌及必要内容摘要识别，索引构建版本还包含解析配置、分块配置和嵌入模型版本；仅模型变化也可能需要重建索引，不能当成原件更新。

版本生命周期：building → ready → active → retired → gc_pending → gc_running → collected；构建可进入 failed/superseded。另设独立 publication_blocked / access_epoch，表示删除、撤权或来源有效性不明。权限状态优先于版本状态，retired 不意味着仍可问答。

发布采用比较并交换：仅当候选仍为最新目标代次、解析完成、来源版本及权限复核通过时切换 active_revision。查询在送入模型前根据权威版本指针与权限过滤候选；索引中残留的 retired 内容不能仅靠元数据缓存而被放行。解析后旧任务完成也不能发布覆盖新版本。

已有流式回答在访问失效后停止继续输出相关内容；实现应在取数、生成前和流式发送检查点复核，必要时取消生成任务。已交付给用户的内容无法追回。回收可以等待有界任务租约释放，但租约不能延长撤权后的阅读权。

### 7.4 默认保留与回收参数

以下为 V1 建议默认值，管理员可在部署策略允许范围内调整；不代表现有实现或性能承诺。

| 对象 | 默认策略 | 回收前提 |
| --- | --- | --- |
| 当前有效版本的知识副本、分块、索引与图片 | 当前版本有效期间保留 | 不受历史数量配额清理 |
| 替换后的旧索引、分块、摘要及专属图片 | 立即退出检索；安全窗口 1 小时后可回收 | 无有效构建/读取租约，无其他有效版本引用 |
| 上一个版本的原件恢复副本 | 最多 1 个旧副本，最长 7 天，以先达到者为准 | 不参与问答；只用于授权恢复；同内容对象不重复保存 |
| 失败或被新版本替代的构建产物 | 任务明确终止后 24 小时可回收 | 已取消后续重试/失效租约；仍需重试的任务另受最大重试期限控制 |
| 构建自动重试 | 默认最长 24 小时，之后转人工可重试状态 | 人工重试建立新任务，必要时重新获取原件 |
| 版本元数据与清理审计 | 90 天 | 不含正文、访问令牌或敏感错误响应 |
| 删除墓碑 | 至少 30 天 | 且超过消息/恢复重放窗口、消费者已确认；不满足则延长并告警 |
| GC 扫描 | 每小时一次；孤立资源核对每日一次 | 分批限流，不阻塞上传或在线问答 |

对确认源文件删除、发布撤回或失去整个绑定读取能力，先禁止访问并取消任务，再尽快清理正文与派生副本，不套用普通版本的 7 天恢复保留。仅单个用户失去权限时撤销该用户访问，不删除仍供其他授权用户使用的共享内容。来源暂时不可达则关闭相关访问、保留数据等待核实，不能按永久删除处理。

Nextcloud 的版本/回收站和备份采用独立生命周期，本集成不反向删除它们，也不假设 Nextcloud 会永久保留某个历史版本。WeKnora 的短期原件副本可提供有限恢复能力，但不是备份。备份还原须重放删除/撤权账本；若墓碑保留时间短于备份恢复窗口，必须延长保留或恢复后在全量核对前保持不可检索。

安全窗口届满后的回收目标为正常负载下 24 小时内完成；超时告警并展示积压，不能仅根据知识记录删除而声称磁盘空间已释放。

### 7.5 持久化回收与数据模型扩展

在第 5 节模型上增加以下逻辑实体，具体表复用在 P0 确认：

- document_revision：稳定来源身份、发布代次、源版本、内容摘要、构建配置指纹、状态、active/retired 时间、保留期限。
- resource_reference：资源所属租户/存储实例、对象 ID、引用版本与用途，区分专属和共享资源。
- gc_job / gc_item：原因、目标版本、对象清单、not_before、每类资源完成状态、重试次数、错误、租约和幂等键。
- publication_ledger：来源删除/撤回与权限代次、消费者确认和恢复检查点。

先持久化待回收清单，再清理业务记录；不能先删掉对象路径后依靠日志猜测残留位置。清理分为取消任务、关闭可见性、清理派生引用、删除索引和数据库内容、删除对象、核对空间及完成审计。每一步独立幂等、可恢复；单一步骤成功不能标记整个任务完成。

资源共享采用引用检查及删除状态保护，引用增加与删除竞争需要数据库事务/锁或等价机制；不能仅用一次非事务 count=0 就删除对象。首版不做跨租户物理去重。恢复与 GC 竞争时只允许一个状态转换成功；对象已删除则从源端重新获取，不恢复悬空引用。

删除只接受持久化记录中的受信对象标识及存储实例，禁止按不受控路径前缀批量删除。孤立资源扫描采用标记后复核，至少跨两个扫描周期并排除活跃任务/临时上传租约，不能仅凭对象创建时间判断无用。

统计分开呈现逻辑用量、已请求删除字节和确认释放字节；底层对象版本控制、快照可能继续占用空间，实际物理容量以存储后端统计为准。

### 7.6 管理功能、容量和实施分工

管理页面增加版本状态、旧副本到期时间、预计可回收量、实际清理状态、失败原因、重试及预览回收清单。员工不看到内部任务 ID 或存储路径。手动立即回收仅限管理员，仍必须通过当前版本、引用和租约检查。

容量采用每知识库保留配额及系统水位共同管理。建议起始水位 80% 告警、90% 暂停新增 AI 入库并优先清理已到期资源；Nextcloud 原件上传是否受限由自身存储策略决定。不能为腾空间删除当前有效版本或未到期恢复副本。水位按实际卷/桶配额分别测量，阈值在试点修订。

P0 明确状态机、权限屏障及存储引用模型；P2 实现独立构建与版本绑定；P3 实现发布比较并交换、GC 清单、回收重试及恢复竞争保护；P4 实现撤权与删除优先级及历史会话约束；P5 完成容量、孤立资源和备份恢复演练。原 P3/P5 工期需在 P0 按新增工作量重估，既有总估算不视为已覆盖全部新增要求。

### 7.7 新增验收用例

1. V2 构建失败：V1 恢复副本仍在，严格最新模式不输出 V1 答案；重试 V2 后恢复问答。
2. V2/V3 连续更新且任务乱序：只能发布目标最新代次；被替代任务不复活，残留进入 GC。
3. V2 发布时向量库仍有 V1：所有检索及引用入口均不使用 V1；模型配置变更可单独重建。
4. GC 每个阶段故障/重启：从持久清单恢复，不重复减存储账，不漏删；失败状态可观测。
5. 两版本引用同一图片：回收其中一个不破坏另一个；并发引用创建与 GC 不产生悬空引用。
6. 单用户撤权：该用户包括历史会话均受限，其他合法用户不受误删除影响；整个来源撤回则关闭全部相关访问。
7. 租约存续时撤权：不得继续输出；物理回收按有界租约协调，超时任务不能永久阻塞清理。
8. 旧引用与恢复：旧回答标明历史版本，回收后不伪造旧原文；恢复产生新代次并重新授权。
9. 容量达到阈值：暂停新增 AI 入库，保留当前知识和文件门户，按优先级清理到期资源。
10. 备份恢复早于删除事件：恢复期间默认不可检索，经账本重放及全量核对后不重新暴露已撤回内容。

### 7.8 Nextcloud 端事件与触发依据

插件采用“事件提示检查 → 读取当前权威状态 → 比对来源记录 → 生成发布动作”的判定链路。事件不是直接执行物理删除的命令。使用目标 Nextcloud 版本支持的公开事件与文件 API，具体事件载荷及存储后端行为在 P0 验证。

| Nextcloud 操作 | 事件或检查信号 | 判定条件 | 生成的动作 |
| --- | --- | --- | --- |
| 新上传/复制文件 | NodeCreatedEvent、NodeCopiedEvent 或完整清单发现新增 | 位于绑定范围，格式允许，符合发布模式，权限可确认 | 新建待发布候选；自动模式入队，人工模式等待发布 |
| 覆盖保存文件 | NodeWrittenEvent 等写入后事件 | 重新读取文件版本，确认内容变化且仍在发布范围 | 创建新的构建代次；不得收到事件就删除旧索引 |
| 文件改名 | NodeRenamedEvent | 来源身份不变，内容不变，仍属同一绑定 | 更新名称、路径及原文入口，不重建内容索引 |
| 文件移动 | 重命名/移动相关事件及目录核对 | 比较移动前后绑定归属；不能仅比较文件名 | 范围内更新元数据；移入建立候选；移出撤回；跨绑定重新授权 |
| 删除/移入回收站 | NodeDeletedEvent、可用的 MoveToTrashEvent 等后置事件 | 已知发布对象确认退出有效文件区 | 先撤回知识，再进入回收流程，不等清空回收站 |
| 从回收站恢复/恢复历史版本 | 目标版本支持的恢复事件、写入/创建事件或核对 | 重新确认身份、内容、范围及当前权限 | 创建新的发布代次；人工模式需重新确认发布 |
| 文件夹整体删除/移动 | 文件夹事件 | 根据旧绑定映射确定所有受影响后代，重新核对范围 | 撤回或更新整个子树，不能只处理文件夹本身 |
| 共享、组成员或高级 ACL 变化 | 可用的授权事件、授权查询及定期核对 | 判断实际访问变化，不假定所有变更都会产生文件事件 | 更新授权代次；单用户撤权不删除共享内容；不支持的权限例外暂停相关发布 |
| 管理员撤回/解除绑定 | 插件明确操作 | 操作者拥有发布管理权限，目标绑定匹配 | 持久化撤回记录，立即关闭相关检索资格 |

Before 类事件仅可辅助捕获删除/移动前身份、路径和绑定，不能据此认定操作成功。以成功后的事件和当前状态确认；失败的删除操作不得触发知识清理。重复事件通过事件 ID 与来源版本幂等合并。移动跨存储或删除后重传可能改变文件 ID，不承诺所有移动都保留身份。

事件丢失由定期核对补偿；外部存储直接变化必须通过 Nextcloud 可验证的扫描/读取机制发现。未经扫描的缓存清单不作为物理删除依据。单次 404、403、网络异常、挂载不可用或分页失败均不能确认永久删除；先暂停受影响访问并排障。完整核对只有在扫描成功、范围未变化且期间变更已协调后才能确认差异删除。

### 7.9 内容变化判断与发布集合

插件记录 instance_uuid、file_id、binding_id、ETag、内容摘要、路径、大小、源更新时间、发布状态和发布代次。文件名/路径是属性，不是身份；修改时间和大小只能辅助筛选，不能单独判定版本。

写入后合并短时间连续事件，重新获取文件元数据；ETag 变化时读取内容并按需计算 SHA-256，下载前后检查版本是否一致，不一致则废弃本次候选并重试。ETag 不假定为内容哈希。内容摘要相同且构建配置未变化时复用已有内容结果，仍独立处理名称、路径和权限变化。摘要不得用于跨租户自动合并知识或泄露文件存在性。

“有效发布候选”需同时满足：文件位于有效文件区、属于已启用绑定范围、符合格式/大小规则、当前权限可确认，以及满足相应模式的发布状态。候选满足条件不代表已可问答；仍需完成构建、授权复核和发布切换。

区分三种结论：

- 明确有效：创建/更新候选，按发布模式处理。
- 明确失效：已删除、移出、主动撤回或替代成功，立即撤回检索资格并安排回收。
- 状态未知：连接/挂载/授权检查失败，暂停访问，保留数据核实，不误报“已删除”。

在自动模式中，只要源端已确认发生可能影响内容的变更，按严格最新策略暂时关闭旧知识；内容核对证明未变化后可恢复。任何模式的权限收紧或删除都优先于内容保留策略。

### 7.10 自动与人工发布模式

V1 默认使用“目录自动发布”：绑定目录是正式资料目录，新文件自动生成发布候选；覆盖同一文件自动更新；移出/删除自动撤回。用户必须知道将文件放入此目录意味着它会进入授权范围内的 AI 知识库。

V1.1 增加“人工确认发布”，对应第 7.2 节审核发布模式，但不默认包含多人审批流程：草稿目录与发布快照分离，发布者执行明确的发布操作，固定发布时的文件版本、内容摘要和绑定范围。后续草稿编辑不会修改已发布快照；快照的删除/撤回/权限收紧仍立即生效。发布快照必须是独立受控对象，不能继续引用可变的草稿路径作为已审批内容。

插件提供以下产品操作：

| 操作 | 权限与条件 | 结果 |
| --- | --- | --- |
| 发布到知识库 | 绑定的发布管理员，源文件可读，目标绑定允许，预览受众和格式检查通过 | 固定候选版本并提交构建；成功后变为已发布 |
| 发布为替代版本 | 同上，且可管理被替代文档；首版仅允许同一绑定内一对一替代 | 新候选成功后切换逻辑文档当前来源，旧知识撤回；原文件保留并标记已被替代 |
| 撤回发布 | 发布管理员拥有目标绑定管理权 | 文件保留在 Nextcloud，知识立即停止被检索，后台回收 |
| 重新发布 | 当前源文件及权限重新检查通过 | 产生新发布代次；不能重放旧批准记录直接恢复 |

自动模式也必须支持管理员“撤回并排除自动重发”。撤回/已替代对象持久化为排除状态，事件和全量扫描均尊重该状态；只有明确的重新发布操作才能解除。手动排除与暂停同步不同，界面分别说明。

绑定不能在两种模式间静默切换。切换前展示受影响范围；转人工模式不得将全部草稿自动发布，转自动模式不得抹除已有撤回/替代排除记录。发布能力若在 V1.1 才交付，V1 界面与文档不能宣称支持人工审批发布。

### 7.11 不同名版本与显式替代模型

“产品手册_V1.pdf”和“产品手册_V2.pdf”默认为两个独立文件；相同文件名、相似标题或内容相似度均不能自动建立替代关系。相似度可作为后续人工提示，不能自动撤回已有文档。

增加逻辑发布文档 publication_document：publication_id、binding_id、current_revision、current_source_ref；增加替代关系 predecessor_revision、successor_revision、操作者、原因、批准时间及排除状态。来源文件身份与逻辑发布身份分离，允许经确认的不同文件成为同一逻辑文档的后继版本。第 5 节 source_mapping 仍记录每个具体源文件，不以逻辑身份覆盖来源证据。

替代操作流程：选新文件 → 选被替代资料 → 展示文件版本、受众和权限差异 → 确认 → 构建新候选 → 复核目标旧代次仍为当前代次 → 原子切换 → 原件标记已替代并排除再次自动发布 → 旧知识进入第 7.4 节回收。

替代构建失败时旧发布保持有效，因为业务替代尚未完成；这不同于自动模式下同一源文件已被修改的严格最新情形。若旧发布在此期间被删除或撤权，必须立即关闭，不能为了可用性继续提供旧答案。并发替代只允许一个切换成功；另一候选显示冲突并要求重新确认，不能产生环形或多义替代链。

首版跨绑定替代被拒绝，避免自动扩大阅读范围。新文件在替代处理期间不得同时作为另一个独立文档自动发布；插件对来源文件及逻辑发布目标记录操作占用和幂等键，明确失败后的恢复状态。

### 7.12 Nextcloud 端新增验收与实施边界

1. 覆盖保存同一文件触发更新；仅改名且内容不变不重建；删除后同名上传按新来源处理。
2. 两个不同名版本不会自动互相替代；显式替代成功后只有新版本可检索，旧原件仍保留。
3. 移入/移出/跨绑定移动及文件夹整体移动均正确处理全部后代；跨存储文件 ID 改变不误合并。
4. 移入回收站即撤回知识；删除操作失败不会误回收；恢复依据模式生成新的候选/发布代次。
5. 手动撤回和已替代原件即使仍在自动发布目录，也不会在下一次事件或全量扫描中复活。
6. 外部挂载失联、部分清单失败或 404 不触发批量物理删除；恢复后核对收敛。
7. 授权变更不依赖 ETag；内容不变但权限收紧时仍拒绝相应访问。
8. 人工模式草稿编辑不改变已发布快照；发布与替代固定内容摘要，处理中再次编辑不偷换审批对象。
9. 替代失败保留仍合法有效的旧发布；并发替代、构建乱序及重试不重复发布、不覆盖新代次。
10. 发布、替代、撤回、排除与重新发布有可审计的操作者、范围、代次和结果；普通员工无法越权执行。

P0 验证事件覆盖与后端身份语义，P2/P3 实现自动模式判断与持久排除，P4 验证权限变化，P5 执行前七项相关验收。人工发布快照和显式替代属于 V1.1 的独立工作包，须额外估算，不视为已包含在原 P6 内嵌问答工期；第 8–10 项在对应能力交付时验收。

## 8. 身份、权限和撤权

V1 两边接同一 AD，分别登录；跳转后由 WeKnora 执行个人登录。使用稳定目录标识及 objectGUID 映射身份，不按邮箱或显示名自动合并。跨系统账号关联冲突由管理员处理。

权限必须满足：WeKnora 当前知识库可读，并且 Nextcloud 当前发布目录对该身份可读。源端授权由插件在明确用户上下文中通过目标版本支持的权限 API 判断，不能只检查同步服务账号是否可读。嵌套组、主组、团队文件夹高级权限的语义在 P0 做验证。

V1 仅允许权限一致的发布目录。对不支持的 ACL 类型拒绝启用；发现后暂停相关发布。来源实时授权检查是事件撤权的补充，不把权限变化发现完全寄托于文件事件。第一版若无法用受支持 API 可靠判断目录内权限一致性，降级为经过验证的专用发布目录模式；仍无法保证则该范围不上线。

WeKnora 为 nextcloud 来源知识库加入统一授权关口，覆盖检索、RAG、知识/分块详情、预览/下载、引用、分享、嵌入、Agent 和工具访问。检索授权发生在内容进入模型前；长任务在取数和输出阶段复核。服务不可用时受影响的来源内容拒绝访问，其他本地知识库照常运行。

首版对 Nextcloud 来源禁用无法继承撤权语义的公共分享、跨库复制/移动、Wiki/图谱跨范围汇总和通用机器 Key 检索；待各路径完成来源授权后逐项开放。入库机器 Key 保留绑定范围内写入能力。历史会话是已披露信息，撤权不能收回用户已下载或已看到的内容；服务端历史消息及引用须采用保守的绑定级访问控制，撤权后不再重新展示相关会话内容。

AD 禁用传播受目录缓存和同步间隔影响，必须测量并明确窗口，不承诺瞬时撤权。插件失联、AD 快照过期、身份无法映射等情况拒绝相关访问。记录首次状态变化、检测、拦截、清理完成时间用于验收。

V1.1 优先复用企业现有 OIDC 身份提供方；若不存在，再评估 Keycloak 等统一身份服务，不默认新建。Nextcloud 后端调用问答接口使用经过验证且限定 audience、scope、有效期的个人授权令牌，服务密钥不得仅凭浏览器提交的 user_id 冒充用户。身份关联、吊销、流式会话续期单独设计。

## 9. 测试与验收矩阵

| 类别 | 必须覆盖的场景 | 通过条件 |
| --- | --- | --- |
| 安装升级 | 新装、启用、禁用、迁移、重启、升级失败恢复 | 配置和状态持久化，禁用插件不破坏文件功能 |
| 文件同步 | 新增、覆盖、连续保存、改名、移动、删除、恢复、中文路径、同名文件 | 身份正确，无重复/复活/跨目录误删除 |
| 异步一致性 | 乱序、重复、下载途中修改、worker 崩溃、游标过期、扫描中变化 | 最终收敛到最新版本，不混用旧索引 |
| 故障恢复 | 网络中断、401/403/429/5xx、部分清单失败、队列积压 | 不误删；自动恢复或给出可操作失败状态 |
| 权限 | 跨部门、禁用用户、组移除、嵌套组、子目录收紧、接口绕过 | 未授权内容不进入检索结果、模型上下文或引用 |
| 入口覆盖 | WeKnora 直接访问、Agent、API Key、分享、历史会话、下载 | 不存在通过替代入口绕过授权 |
| 运维 | 密钥轮换、备份恢复、版本回退、磁盘不足 | 可恢复，映射与索引核对完成，失败不扩大访问 |

测试分层：PHP 单元/Nextcloud 集成、Go 单元及数据库测试、双方 OpenAPI 契约、浏览器端到端、隔离故障注入、容量压测。使用模拟目录及脱敏文件；真实企业 AD 生命周期测试在隔离测试账号/组完成。

初始试点负载假设：20 名用户、2 个部门、1 万文件、100 GB 原件；这些是测试设计假设，不是实测规模。企业已同步用户数量不等于并发容量。

建议性能目标：在明确硬件和负载下，事件到任务持久化 P95 ≤ 10 秒，空闲队列的小型文本入库 P95 ≤ 60 秒，开启集成后上传 P95 延迟增幅 ≤ 10%。扫描/OCR、大文件和模型吞吐另列基线，不混算。来源已可观察的撤权后，新的授权检查拒绝访问；AD 变更到源端可见的时延单独记录。目标在 P0 固化、P5 实测，未达标必须说明原因和调整方案。

## 10. 运维、容量、发布与恢复

部署配置包括 HTTPS、受信域名/代理、企业 CA、LDAP、团队文件夹、上传限制、临时目录、后台 worker、持久卷、健康检查和资源限额。存储容量预算包含原件、版本/回收站、WeKnora 入库副本、解析图片/索引、备份和至少预留的运维空间，按样例实测放大，不用原件体积直接估算总容量。

指标包含 outbox/inbox 积压、最老任务年龄、同步延迟、失败率、解析耗时、授权拒绝/异常、最后成功核对时间、存储使用量、备份时间和恢复验证时间。日志以 trace_id、binding_id、event_id 关联，禁止记录正文及凭据。

备份覆盖 Nextcloud 数据库、配置、数据目录/对象存储与插件状态，以及 WeKnora 数据库、原件副本、必要索引、加密密钥。跨服务备份采用暂停发布/同步后的协调检查点；恢复先关闭检索与同步，核对身份、绑定和版本后再开放。索引可重建，但重建时间计入恢复目标。建议试点 RPO 24 小时、RTO 4 小时，需恢复演练验证。

先本地联调、再测试环境、再两个部门试点，最后扩大范围。应用发布包、镜像摘要、数据库迁移、兼容矩阵和验收报告一起版本化。回滚先停集成与检索，保留 Nextcloud 文件入口；应用代码可回退不代表数据库可自动降级，破坏性迁移须备份恢复或前向修复。正式部署作为开发验收后的独立执行步骤。

V1 合计约 37–54 工程人日；两名工程师考虑串行依赖与联调，建议按 6–8 周规划，额外预留 20% 风险缓冲。V1.1 再预留约 2–3 周，新增身份基础设施可能延长。V2 在 V1 数据和权限验证后另行估算。

## 12. 交付物与完成定义

交付物：Nextcloud 部署项目、可安装插件包、WeKnora 连接器及权限补丁、OpenAPI/事件规范、迁移脚本、测试与脱敏样例、CI 配置、镜像/应用版本清单、管理员/员工手册、备份恢复与回滚手册、性能与权限验收报告。

完成定义：全新环境按文档成功启动；从上传到问答/原文闭环可用；更新删除与权限撤销通过；服务中断不阻塞员工文件上传；任务恢复不重复或误删；备份恢复演练完成；没有开放的越权、数据丢失或旧任务复活缺陷；明确记录尚未支持的文件类型和权限模式。

## 13. 启动时需固化的信息

P0 固化：正式域名与证书、部署主机/存储容量、文件数量/类型/大小分布、峰值上传与问答并发、试点部门/AD 组、是否已有 OIDC、备份保留周期与 RPO/RTO、是否需要公网访问。未确定前采用隔离开发环境、模拟组、单机 Compose 和两个测试部门，不阻塞代码骨架及契约验证。
