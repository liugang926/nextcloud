## Concrete normal-app drill sequence

1. **Fresh owned start.** Use a newly prepared marker-owned direct/nested LDAP fixture and the exact normal candidate image ID, `--body-journal`. Pin NC/app/database/docreader/mock model images and source commits. Run fixture bootstrap and actual directory/source permission matrix. A ready signed file status must match the current file ETag; Alice guarded knowledge/chunk access and first QA must succeed. Persist session/message IDs and original citations privately, with public evidence containing only IDs/digests/booleans. Require actual message original admission/material/generation origin and body-head coverage, and completed task/Auto receipts; do not reconstruct old originals from current text.

2. **Record scope/identity.** Capture NC instance ID, publication binding/root/file IDs/ETag, pairing operation and key IDs (no key bytes), WK tenant/KB/source IDs and configuration/routing digests, active signed event connection ID, directory/objectGUID/group-grant snapshot, source/current version/fence epochs, model catalog digest and body journal UUID/sequence/head digest. Include full database migrations, body payload/head/revision/parent/lease/purge metadata counts,150/151 message tables and153 publication transitions/SQL intent metadata. Treat ID/hash snapshots as scope checks, not authorization substitutes.

3. **Quiesce.** Verify sender source outbox received/applied is drained; no running sync, pending/finalizing parse, pending/running Auto intent, live scoped content lease or original body lease remains. Stop the probe-owned sender, normal `wk-app` and any reader/native stream; confirm exact Docker IDs/owner labels/pinned images and stopped states. Put NC in maintenance, stop NC ingress/background writers. Do not globally kill shared services. Data queues stop generating work; Redis data may be archived as recovery evidence but is not an authorization source for replay.

The fully drained checkpoint is a stable whole-app restore case; it cannot demonstrate recovery of a pending153 intent. Add a separately labelled pending-Auto case only if a real signed ingest and an actual bounded queue outage/process crash produce `Completed` plus the server-sealed SQL intent before delivery. Observe its actual queue/model manifest body heads, payload digest, current lease/fence identity and pending state; never insert a fake pending row or construct a receipt. Stop all remaining actors before dumping. After restore keep Redis empty/untrusted, let the actual startup SQL outbox recovery reenqueue the exact intent, and verify one model/tag publication and terminal SQL state. Repeat a closed/withdrawn-source variant to prove the old task cannot revive. If that real boundary cannot be captured, keep whole-app pending-Auto restore unaccepted and cite only the existing package fault evidence.

4. **Checkpoint full data.** Under0700 evidence and0600 files, run actual `pg_dump -Fc` for both DBs, plus cluster role/global backup where needed.
