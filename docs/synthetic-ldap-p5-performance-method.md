# P5 method for one owned synthetic LDAP candidate

No latency or upload result has been measured by this change. The current normal candidate image and its fresh owned scratch directory must be supplied by the parent application acceptance task. Offline checks exercise the measurement method only.

Use `scripts/ops/synthetic-ldap-performance.py --scratch PATH --samples 100 --mode all`. It accepts only the existing `synthetic-ldap-fixture.py` marker, exact Compose fingerprint, resource owner labels and pinned app image. It uses `runtime.json` / `fixture.json`, the actual `synthetic-published` binding and the already provisioned signed event connection. It creates only a nonce-owned synthetic subfolder and files, keeps private reports under the owned scratch directory and retains everything for the parent owner's final destruction. It does not create another stack, pair or event credential.

## Exact endpoints and timing

The historical `pilot-load.py` requires two `pilot-*` projects, a particular two-network attachment and a pilot binding ID. Its event cursor measurement does not establish per-file readability or upload on/off overhead. This new probe keeps its nearest-rank percentile method while using the single synthetic project's ownership verifier.

Each of at least100 event samples starts only after actual SQL shows no running source sync, no pending/processing/finalizing knowledge, no staging source version, no pending Auto intent and no live content/body lease in the KB; the source sender and receiver must cover the actual source outbox watermark, and the applied cursor must cover that received cursor. This prevents a still-unsent hint from being mislabeled idle. A unique 1KiB synthetic file is uploaded through actual WebDAV. Its exact file ID/ETag and a new upsert event ID are observed. Different samples must have different file IDs, event IDs and admitted sync log IDs, so a coalesced batch cannot be counted100 times.

- **Event to durable job:** host monotonic time immediately before WebDAV PUT through the first scoped observation of the dispatched cursor covering that exact event. `NextcloudEventDispatcher.dispatchOne` persists a log ID through `PrepareDispatch`, sends task ID `ncevent:<connection>:<log>`, then calls `FinishDispatch` only after queue acceptance. The probe reports that actual ID and a conservative upper bound which includes PUT, SQL request and observation time. It does not confuse received or applied with durable queue acceptance. Nextcloud's persisted outbox timestamp is only second precision, so no sub-second cross-host subtraction is claimed.
- **Idle small text to a new readable version:** the same PUT start through the exact current ETag reaching the session-scoped Nextcloud Files status route, which validates the paired machine status signature and rechecks Alice's source access. Scoped SQL identifies the published candidate. Alice's LDAP token must then obtain HTTP200 for that exact knowledge and a nonempty guarded chunk list. The probe emits booleans and timings, never response text.
- **Upload overhead:** at least100 on PUTs and100 off PUTs in capped ABBA blocks. Both conditions use fresh unique 1KiB files in the same owned binding subtree. Every on PUT starts idle and its processing drains before the next upload. Only the PUT response duration contributes to upload latency. Off samples run with `integration_weknora` disabled after actual idle and zero leases, the probe sender stopped and the same owned `wk-app` stopped, so a missing route cannot perturb an asynchronous builder. On first restores the NC app, starts the same pinned `wk-app`, refreshes login, verifies unchanged original source/binding/pair/model/journal/baseline-generation identity, reconciles the off files and verifies actual idle. Restart/reconciliation warmup intervals are separately recorded and excluded. `finally` restores the enabled app and stops the probe-owned sender.

The reported P95 is nearest-rank `ceil(0.95*N)`. Targets are durable-job upper P95≤10000ms, idle-readable upper P95≤60000ms, and `100*(on_P95/off_P95-1)`≤10%. Failures and partial observations remain evidence; failed samples are not silently omitted and no target is relabeled as passed.

## Scheduling and resource bounds

This synthetic fixture has no default `cron` or `event-worker` service. The probe explicitly runs the **real** bounded `php occ integration_weknora:deliver-events --quiet` CLI inside its already owned Nextcloud container, then sleeps5 seconds. The CLI is bounded by90 seconds, with a5-second kill grace; pass durations are recorded. This is a probe-owned external worker, not a claim that the fixture or production deploy defaults contain one.

The source's TimedJob uses60 seconds, the ordinary external sender script sleeps5 seconds, and the WeKnora dispatcher defaults to5 seconds (allowed1s..1min). Queue/publication rechecks also have a5-second interval. Even an idle5s sender plus5s dispatcher can consume nearly the entire10s target before network/processing cost. No dispatch interval or production default is changed by this probe. Any future optimization must follow actual measured cause and update deployment defaults/documentation consistently; a faster benchmark flag alone cannot count as acceptance.

The observation sleep is0.5 seconds, but HTTP/SQL requests add time. Every sample records the measured maximum request-start-to-next-response-end interval instead of pretending0.5 seconds is its complete observation bound. All raw per-sample observations are flushed and fsynced to a0600 JSONL file as they happen. The final0600 JSON report includes sample IDs, ETag hashes, queue IDs, timings, actual container image/resource limits, Docker host CPU/memory/architecture, verified local mock model configuration digest, sender passes and excluded warmups. Limits of0 mean unenforced, not zero available resources. It contains no credentials, source text or SSE.
